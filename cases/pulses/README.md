# Pulse files: setting up a new shot in PDS

This guide takes you from a DINA shot number to running PDS simulations of it. It
assumes you know the physics but not PDS.

## What a pulse file is

A pulse file is one YAML file per shot, `cases/pulses/<shot>.yaml`. It is the **only**
place where shot-specific choices are made: which DINA entry to read, how many time
slices to prepare, which time window to simulate, which transport settings to use,
which times to plot.

`bin/pds-configure` reads the pulse file and derives every other file from it:

| Generated file | Content |
|---|---|
| `<SCENARIOS_REPO>/<shot>/source.env` | inputs of the data preparation (`preprocessing/prepare`) |
| `cases/overrides/generated/<wf>_<shot>.ymmsl` | per-workflow settings (time window, time steps, loop tuning) |
| `cases/overrides/generated/<wf>_<shot>_config_torax.py` | only if `transport_calibration` is set: a calibrated TORAX configuration |

`cases/overrides/generated/` is git-ignored: generated files are never committed, they
are recreated from the pulse file. Each generated file starts with a
`# GENERATED by bin/pds-configure ...` line: do not edit these files, edit the pulse
file and rerun `bin/pds-configure` (or make a hand-written copy, see
[Override precedence](#override-precedence)). The validation plot
times (`postprocess.t_list`) are read by post-processing directly from the pulse file.

`cases/pulses/TEMPLATE.yaml` lists every key with a comment; the full reference is the
docstring of `pds/configure.py`. Unknown keys are reported as errors.

## Overview

```
Step 0  edit   cases/pulses/<shot>.yaml
Step 1  bin/pds-configure cases/pulses/<shot>.yaml --prepare
Step 2  bin/pds-configure cases/pulses/<shot>.yaml --create
Step 3  bin/pds-run-case cases/<workflow>_<shot> [cases/quick_test.ymmsl]
```

## Prerequisites

- An SDCC login.
- Nothing to check out besides PDS: the preparation tooling is in `preprocessing/`
  (guide: [`preprocessing/README.md`](../../preprocessing/README.md)). The prepared data
  go to the scenario data root `SCENARIOS_REPO`, by default `scenarios/` in this checkout
  (generated, not committed). To use another data root, e.g. the shared
  `/work/projects/pds/pds-scenarios`, `export SCENARIOS_REPO=<path>` before running
  `bin/pds-configure`. Cases made with `--create` record that data root in their
  `case.env`, so you do not need to export it again when you submit runs.
- Nothing else to load: `bin/pds-configure` loads the `IMAS-MUSCLE3/1.0.0-intel-2025b-pds`
  module itself if it is not already loaded.

All commands below are run from the root of the PDS checkout.

## Step 0 - Configure the pulse

The pulse file is the **only** file you edit. Do this before anything else, and again
every time a choice changes:

```bash
cp cases/pulses/TEMPLATE.yaml cases/pulses/<shot>.yaml
```

(for 105033 this already exists, so start from `cases/pulses/105033.yaml` if you are
looking for a worked example).

Fill in:

- `shot`: the DINA shot number.
- `prepare.source`: the DINA entry. Use the official store,
  `imas:hdf5?path=/work/imas/shared/imasdb/ITER/3/<shot>/<run>`. Entries under personal
  home directories are not official.
- `prepare.machine_description: basic`: the current ITER machine description (active
  ITER_MD catalogue versions: pf_active 111001/204, pf_passive 115005/3, wall 116000/5;
  ITER has no iron core, so iron_core is `empty`: the converter creates an empty
  static iron_core IDS). The set `legacy`
  (111001/203, 115005/2, 116000/4) is what the five pds-scenarios scenarios
  105073/78/84/92/99 were prepared with; use it only to reproduce them.
- `prepare.dd_version` (optional, default `"4.0.0"`): the Data Dictionary version the
  prepared data are written at (exported as `IMAS_VERSION` to the preparation). 4.0.0 is
  the version of the stored data of the existing scenarios; keep it unless you know
  every workflow you use reads another one.
- `prepare.n_timeslices`: the number of time slices to prepare. This sets the **outer time
  grid** of the simulation: slices are chosen uniformly in time over the viable part of
  the pulse (|Ip| > 50 kA and magnetic axis R > 1 m). Picks that are not viable are
  skipped, so you may get one or two fewer slices than requested.
- `workflows`: the workflows to set up. `TEMPLATE.yaml` (and 105033) list all five
  supported ones; remove those you do not intend to run.
  **This list controls two things: which workflows `bin/pds-configure` generates an
  override for (`cases/overrides/generated/<workflow>_<shot>.ymmsl`, applying this pulse
  file's time window, steps and calibration), and which workflows `--create` builds a
  case folder for (`cases/<workflow>_<shot>/`).** A workflow left out gets no generated
  override; running `bin/pds-create-case <workflow> <shot>` for it by hand then falls
  back to that workflow's generic settings only (e.g. the whole prepared time window,
  which for 105033 would include the early limiter slices NICE inverse cannot solve),
  unless a hand-written override exists for it. `[]` means preparation and plot times
  only (used by the five legacy pulse files, whose run settings are in hand-written
  overrides): `--prepare` works, `--create` has nothing to create. See "Choosing the
  workflow" below and "The legacy shots" for why those stay `[]`.
- `time.t_start` / `time.t_end` set: inverse_convergence `loop.t_min` / `loop.t_max`,
  prescribed_transport `source.t_min` / `source.t_max`, the METIS workflows
  `source_metis.t_min` / `source_metis.t_max` (see "METIS time window" below), and the
  default evolutive_controller forward window.
- `time.t_start`: at or after the **first diverted slice**. NICE inverse cannot solve
  limiter plasmas. Example: 105033 is limiter until 9.23 s and diverted from 12.23 s,
  so `t_start: 12.0`.
- `time.t_end`: before the last viable slice.
- `t_start` and `t_end` only **select** slices from the prepared grid; they do not create
  new ones. For more slices, raise `n_timeslices` and rerun Step 1.
- `time.transport_dt`: TORAX's internal time step between two slices in
  inverse_convergence (default 0.3 s).
- `time.forward_dt` and `time.forward_source_dt`: only for evolutive_controller.
- `time.forward_t_start` / `time.forward_t_end` (default `t_start` / `t_end`): the
  evolutive_controller forward window (`source.t_min` / `source.t_max`; `forward_t_end`
  also sets `torax.t_final` and `nice_evo_rd.t_end`). It must lie inside the inverse
  result the forward run starts from, and `forward_t_start` should be one of its native
  slices (on 105073 a start from a non-native slice diverged).
- `time.forward_source` (optional): URI of that inverse result (`source.source_uri`).
  Default: the `out_nice` of the latest `inverse_convergence` run of the same shot,
  `cases/runs/inverse_convergence_<shot>/out_nice`.

Whenever evolutive_controller is selected, `bin/pds-configure` (also with `--dry-run`)
checks the forward window against that source before writing anything: if it is a
local HDF5 entry that exists, a window outside its equilibrium time range is an error,
and the first native slice of the window is logged (with a warning, quoting the nearest
native slices, if `forward_t_start` is not one of them); if the source is not a local
HDF5 entry or does not exist yet (no inverse run so far), only a warning is printed.
- `postprocess.t_list`: three times for the profile plots, typically one in ramp-up, one
  mid-flattop and one in ramp-down.

To see whether a time window is reasonable before preparing anything, look at the raw
pulse:

```bash
bin/pds-configure cases/pulses/<shot>.yaml       # first, if source.env does not exist yet
module load IMAS-MUSCLE3/1.0.0-intel-2025b-pds
python preprocessing/check_scenario.py <shot>    # writes $SCENARIOS_REPO/<shot>/check_<shot>.png
```

`check_scenario.py` reads the raw DINA summary via `<SCENARIOS_REPO>/<shot>/source.env`
(`SOURCE_URI`/`SUMMARY_URI`), which a plain `bin/pds-configure` call (no `--prepare`/
`--create`) already writes; only the read of the *prepared* entry (`data/in`, written by
Step 1) is wrapped in a try/except, so the raw-pulse plot (Ip trace, viable window,
flattop) works even with nothing prepared yet, and a WARN about the prepared equilibrium
is expected until Step 1 has run. The plot written this way, or the one `--create` draws
in Step 2, shows the same Ip trace, prepared slices and flattop.

Depending on which keys you change, rerun only the corresponding steps:

| Keys you change | Then rerun |
|---|---|
| `prepare:` (source, machine_description, n_timeslices, md_layout, dd_version) | Step 1 (`--prepare`), then Step 2 (`--create`) |
| `time:`, `workflows:`, `transport_calibration:` | Step 2 (`--create`) only |
| `postprocess.t_list` | nothing: read from the pulse file at the end of each run |

Never edit the files generated from the pulse file: `scenarios/<shot>/source.env`,
`cases/overrides/generated/<workflow>_<shot>.ymmsl`,
`cases/overrides/generated/<workflow>_<shot>_config_torax.py`.
Their first line says so, and the next `bin/pds-configure` call rewrites them -- every
call, with or without options, rewrites them.

### Choosing the workflow

`workflows:` names one or more folders under `workflows/`. **Each entry gets a
generated override (time window, steps, calibration) from every `bin/pds-configure`
call, and gets a case folder `cases/<workflow>_<shot>/` from `--create`** — so each
listed workflow costs a `--create` case build (METIS cases also run MATLAB
preprocessing at creation); list only the workflows you intend to run. The pulse
generator (`bin/pds-configure`) supports:

- `inverse_convergence`: NICE inverse + TORAX, iterated to convergence.
- `prescribed_transport`: NICE inverse with DINA profiles prescribed, no TORAX.
- `evolutive_controller`: forward NICE evolutive + TORAX + magnetic controller; needs a
  finished `inverse_convergence` run of the same shot to start from (or
  `time.forward_source`), and its time window (`time.forward_t_start` /
  `forward_t_end`) normally differs from that inverse run's. Run inverse_convergence
  first, then rerun `bin/pds-configure cases/pulses/<shot>.yaml --create` (or with
  `--workflow evolutive_controller --create`) so the forward window is checked against
  the actual inverse result.

- `metis_from_dina`: METIS transport on the DINA input, no NICE.
- `metis_nice_inverse_from_dina`: METIS transport, then a NICE inverse solve on each
  METIS equilibrium.

The two METIS workflows do not read the prepared `data/`: their own `preprocess.sh`
builds the METIS input (and, for the NICE variant, the DINA-derived NICE input) from
`<SCENARIOS_REPO>/<shot>/source.env` into `cases/<wf>_<shot>/preprocess/` when the case
is created, with MATLAB (several minutes per case). They therefore need neither
`preprocessing/prepare --metis` nor `md_layout: separate` (a `combined` shot is accepted
for them). `time.transport_dt` and `transport_calibration` do not apply (no TORAX; an
INFO line says so).

#### METIS time window

Verified in the code (IMAS-MUSCLE3 1.0.0 `imas_muscle3/data_sink_source.py`, METIS-IRFM
2026.08-pds `workflow/muscle3/mfile/`):

- `source_metis` is an imas_muscle3 `source_component`. Its `t_min` / `t_max` bound the
  native time array of its input, and with `iterative` left at its default (true) it
  sends **one slice per message** for every native slice in `[t_min, t_max]`, chaining
  `next_timestamp` (`None` on the last). The first slice METIS sees is therefore the
  first native slice of `preprocess/metis_in` at or after `t_start`.
- METIS (`metis4muscle3`, `metis_clock_internal` off by default) takes `t_cur` from the
  received message timestamp and `t_next` from its `next_timestamp`; its
  `metis_clock_time_start` is used only with the internal clock or in replay mode, and
  `metis_clock_time_stop` defaults to infinity. So no METIS setting has to be matched to
  the window and none is written.
- In metis_nice_inverse_from_dina, `source_nice` is a `sink_source_component`, not a
  `source_component`: it has no `t_min` / `t_max` and re-slices its input at the
  timestamp of each METIS equilibrium it receives. The window reaches NICE through
  METIS, so only `source_metis` is bounded.

### When a workflow fails

Errors in the pulse file itself (unknown keys, wrong types, a `--workflow` that is not
listed) stop `bin/pds-configure` at once, as do failures common to all workflows
(`source.env`, `--prepare`). A failure of **one** workflow -- generating its override, its
check (typically the evolutive_controller forward-window check before a full
inverse_convergence run exists), the overwrite guard of its files, or its
`pds-create-case` (e.g. a METIS MATLAB preprocess error) -- is reported as
`error: <wf>: ...`, that workflow is skipped and the others are still generated and
created. The command then exits with code 1 and ends with
`failed workflows: <list> (succeeded: <list>)`. Fix the cause and rerun, if needed with
`--workflow <wf>` for the failed one only.

## Step 1 - Prepare the data

```bash
bin/pds-configure cases/pulses/<shot>.yaml --dry-run    # show what would be written
bin/pds-configure cases/pulses/<shot>.yaml --prepare
```

`--prepare` writes `<SCENARIOS_REPO>/<shot>/source.env` and runs
`preprocessing/prepare` (details in [`preprocessing/README.md`](../../preprocessing/README.md)),
which:

- selects the time slices (see `n_timeslices` above);
- converts the DINA data to Data Dictionary 4 (`prepare.dd_version`, default 4.0.0);
- adds the machine description;
- for older DINA runs with 12 PF coils, converts them to the current 14-coil layout,
  following the DINA developer's conversion script;
- snaps the end of the radial grid to exactly 1.0 when it is within 1 % of it.

Expected messages, all harmless:

- a message about the coil-count conversion (12 -> 14 coils);
- messages about snapping rho to 1.0;
- a `RuntimeWarning: divide by zero` from the imas library;
- fewer prepared slices than requested (non-viable picks skipped).

## Step 2 - Create the cases

```bash
bin/pds-configure cases/pulses/<shot>.yaml --create
```

This writes the override files, runs `bin/pds-create-case` for each workflow, appends
`export SCENARIOS_REPO=<data root>` to `cases/<wf>_<shot>/case.env` and writes
`cases/<wf>_<shot>/check_<shot>.png`. Look at that figure before submitting.

Equivalent by hand:

```bash
bin/pds-configure cases/pulses/<shot>.yaml        # writes source.env and cases/overrides/generated/<wf>_<shot>.ymmsl
export SCENARIOS_REPO=$PDS_REPO/scenarios
bin/pds-create-case <workflow> <shot>             # once per workflow listed in the pulse file
```

`--create` also records the data location in each case's `case.env` and draws
`cases/<wf>_<shot>/check_<shot>.png`; without `--create`, `SCENARIOS_REPO` must also be
exported when submitting the run (see Step 3).

**Warning:** `bin/pds-create-case` and `bin/pds-run-case` default `SCENARIOS_REPO` to
`/work/projects/pds/pds-scenarios` (the shared, older data; it has no 105033) when the
variable is not set, whereas `bin/pds-configure` defaults to `$PDS_REPO/scenarios`. Export
`SCENARIOS_REPO` explicitly, or use `--create` (which records it in `case.env` for you),
to avoid silently picking up the wrong data root.

Rerun this step after **every** change of the pulse file (see the key/rerun table in
Step 0).

## Step 3 - Run

```bash
export PDS_REPO=$PWD
```

`SCENARIOS_REPO` need not be exported: the case's `case.env` (written by `--create`)
sets it for post-processing, and the case's ymmsl files already contain the data paths.

Quick test first:

```bash
bin/pds-run-case cases/inverse_convergence_<shot> cases/quick_test.ymmsl
```

`cases/quick_test.ymmsl` is an **overlay**: extra settings stacked last, for this run
only. It limits the run to the first 3 slices of the window and one outer iteration;
the case itself is unchanged.

Full runs, without the overlay:

```bash
bin/pds-run-case cases/inverse_convergence_<shot>
bin/pds-run-case cases/prescribed_transport_<shot>
```

`bin/pds-run-case` is a thin `sbatch` wrapper around `bin/pds-run-case.sbatch` (it falls
back to running that script directly under bash if `sbatch` is not on `PATH`). To
override Slurm resources (time, cpus, ...), submit the sbatch script directly instead:

```bash
sbatch --time=00:20:00 --cpus-per-task=8 bin/pds-run-case.sbatch cases/prescribed_transport_<shot>
```

prescribed_transport has no TORAX and always runs the full window.

Outputs go to `cases/runs/<case>_<timestamp>/` (`out_nice`, `out_torax`, `plots/`);
`cases/runs/<case>` is a symlink to the latest run.

Workflow chain: evolutive_controller starts from the NICE output of a finished
inverse_convergence run of the same shot, so run inverse_convergence first.

## TORAX transport and the chi multipliers - practical guide

**Default: omit `transport_calibration`.** The workflows then use TORAX's QLKNN model, a
neural-network surrogate of a turbulence code. It has no chi multipliers and needs no
per-shot tuning. Start every new shot this way.

**What the multipliers are.** They exist only with the simpler Bohm-gyroBohm model
(`model: bohm-gyrobohm`), where each heat diffusivity is a model coefficient times a
multiplier. There are four multipliers (electron/ion x Bohm/gyroBohm), TORAX default 1.0.
A larger multiplier means more transport, hence lower temperatures and lower stored
energy (roughly W_th ~ 1/multiplier).

**When to use it.** Only if QLKNN is unsuitable for the shot (for example, its TORAX
temperatures clearly deviate from DINA in the validation plots) and you want a model you
can tune against DINA.

**Format.**

```yaml
transport_calibration:
  model: bohm-gyrobohm
  chi_multiplier: 1.8                       # constant, or:
  # chi_multiplier: {0: 1.8, 140: 1.8, 175: 4.0}
  # chi_e_gyrobohm_multiplier: 1.0          # per-channel keys override chi_multiplier
```

- The keys of a table are **times in seconds** (not slice numbers). TORAX interpolates
  linearly between them and keeps the first/last value outside the range.
- `chi_multiplier` sets all four multipliers; `chi_e_bohm_multiplier`,
  `chi_i_bohm_multiplier`, `chi_e_gyrobohm_multiplier`, `chi_i_gyrobohm_multiplier`
  override individual ones.

**How to fill it, step by step.**

1. Run inverse_convergence once with
   `transport_calibration: {model: bohm-gyrobohm, chi_multiplier: 1.0}`.
2. Compare TORAX with DINA in the run's `plots/`:
   `pds_core_profiles_<shot>.png` (Te, Ti at the `t_list` times),
   `pds_equilibrium_0D_<shot>.png` (beta_pol vs time, a proxy for stored energy) and
   `pds_rlte_<shot>.png`.
3. Where TORAX is too hot or beta_pol too high in a phase, raise the multiplier there,
   roughly by the ratio TORAX/DINA of that quantity; where it is too cold, lower it.
4. Place the time knots at the phase boundaries seen in the check plot (end of ramp-up,
   start of ramp-down) and keep the value constant within a phase.
5. Rerun Steps 2-3 and iterate once or twice. One to three knots per phase is enough.

**Worked example, 105073.** Bohm-gyroBohm with default multipliers gave about 40 % too
much flattop thermal energy and no temperature drop in ramp-down. Hence
`chi_multiplier: {0: 1.8, 140: 1.8, 175: 4.0, 205: 4.0}`: 1.8 through flattop, ramping
to 4 over 140-175 s, 4 afterwards. These knots are specific to that pulse's timing;
never copy them to another shot.

## Override precedence

For `bin/pds-create-case <workflow> <shot>`, the shot's override (copied into the case
as `scenario_settings.ymmsl`) is the first of:

1. the hand-written `cases/overrides/<workflow>_<shot>.ymmsl`;
2. the generated `cases/overrides/generated/<workflow>_<shot>.ymmsl`;
3. none: the workflow's generic settings only.

It prints which one it used. The choice is per whole file: a hand-written override
replaces the generated one entirely, the two are never merged. `bin/pds-configure`
warns when a hand-written override shadows the file it generates (and still writes the
generated file).

To customise a generated override beyond what the pulse file offers:

1. Copy `cases/overrides/generated/<workflow>_<shot>.ymmsl` to `cases/overrides/`.
2. Delete its first line (the `# GENERATED by bin/pds-configure` marker) and edit it.
3. If it sets `python_config_module` to a generated `<workflow>_<shot>_config_torax.py`,
   copy that file to `cases/overrides/` too and change the path in the override to
   `${PDS_REPO}/cases/overrides/<workflow>_<shot>_config_torax.py`.

From then on the pulse file no longer affects that (workflow, shot) case settings:
`time:` or `transport_calibration:` changes must be carried over by hand. Delete the
hand-written copy to go back to the generated one.

## The legacy shots and cases/overrides

`cases/overrides/` holds, per (workflow, shot), settings that `bin/pds-create-case`
stacks on top of the workflow's generic settings, plus companion files they point to:
`_config_torax.py` (a TORAX configuration), `_config_nice_inverse.xml` (NICE settings)
and `_waveforms.yaml` (a waveform-editor design).

The override files for 105073, 105078, 105084, 105092 and 105099 are hand-written, so
by the precedence rule above they always win over anything generated.
`bin/pds-configure` writes only into `cases/overrides/generated/` and never touches
them. Their pulse files have `workflows: []`: they only drive
data preparation and the raw-pulse plot times, not case generation. They deliberately do
not list the five workflows of the template: for every listed workflow without a
hand-written override (e.g. the METIS workflows or prescribed_transport for most of these
shots) a generated override would be created and `--create` would build a case with it,
changing how those workflows run for these shots.

## Tips and troubleshooting

- **Post-processing fails looking in `/work/projects/pds/pds-scenarios`**: the case was
  not made by `bin/pds-configure --create` (its `case.env` has no `SCENARIOS_REPO`).
  Rerun Step 2, or export `SCENARIOS_REPO` when submitting.
- **"exists and was not generated by bin/pds-configure"**: a file in
  `cases/overrides/generated/` without the GENERATED line is never overwritten. Move it
  away (hand-written overrides belong in `cases/overrides/`), or rerun with `--force`.
- **"hand-written override ... takes precedence"**: a `cases/overrides/<wf>_<shot>.ymmsl`
  exists, so the generated file is ignored by `bin/pds-create-case` (see
  [Override precedence](#override-precedence)). Delete it if it is not wanted.
- **WARN "time array not strictly increasing"** (a duplicated first slice): harmless if
  `t_start` excludes that slice.
- **A run failed**: look at `cases/runs/<run>/muscle3_manager.log` first (which component
  stopped), then `cases/runs/<run>/instances/<name>/stderr.txt` for that component.
